# Client Aloha Vue Modal

Этот skill задаёт структуру прикладных модальных окон. Используй его вместе с [client-aloha-vue](../client-aloha-vue/SKILL.md) и соблюдай соглашения клиентского проекта.

## Выбор окна и документация

Для простого модального окна без формы используй `AModal`. Если окно содержит форму, используй `AModalForm`. Для простого подтверждения действия используй `AConfirmAPI`; не создавай форму для вопроса с кнопками подтверждения и отмены.

В пакете Aloha-Vue прочитай `llms/components/modal.md` и, для форм, `llms/components/form.md`. Для подтверждений — `llms/components/confirm.md`. Если нужный контракт не описан полностью, проверь `src/AModalForm/AModalForm.js`, `src/AModal/AModal.js`, `src/ui/AForm/AForm.js` или `src/compositionAPI/AConfirmAPI.js`.

## Структура модальной формы

Называй компонент `<Name><Action>Modal`, например `UserCreateModal`, `UserUpdateModal` или `UserCreateOrUpdateModal`. Размещай в `views/<Page>/Modals/` по структуре клиента.

Основной JavaScript компонента собирает composition-функции, выполняет явную инициализацию и возвращает API шаблона. Создавай только необходимые файлы:

| Файл | Ответственность |
| --- | --- |
| `ModelAPI.js` | `model = ref({})`, начальные значения и `initModel`, если требуется |
| `DataFormAPI.js` | `dataForm`: поля, их настройки, варианты выбора и вычисляемые состояния |
| `SaveAPI.js` | `save`, `saving`, `errors`, запрос сохранения и обработка результата |
| `HeaderAPI.js` | Вычисляемый заголовок и подписи, если они различаются для create/update |

Другие API добавляй для самостоятельной логики задачи. Не создавай `HeaderAPI` ради постоянной строки и не добавляй пустые заготовки.

Composition-функции принимают не более трёх аргументов: `(props, context, { дополнительные параметры })`. Контекст деструктурируй, например `{ emit }`. Дополнительные параметры записывай каждый с новой строки, по алфавиту, со значениями по умолчанию, показывающими ожидаемый тип; объект по умолчанию — `{}`. Не меняй фиксированные позиции аргументов, если какой-то из них не используется.

## Модель и режим окна

В `ModelAPI` создавай собственную модель формы. Для update явно переноси нужные поля исходного объекта, не связывай редактируемые вложенные объекты и массивы с исходной записью. Отмена не должна менять данные страницы.

Добавляй `initModel`, когда нужна подготовка модели из записи, преобразование форматов или разные начальные значения create/update. Вызывай её явно из основного файла компонента. Watchers и lifecycle hooks также оставляй там. Учитывай повторное открытие и смену редактируемой записи; не сбрасывай ввод пользователя из-за несвязанного обновления props.

Если нескольким API нужен режим create/update, вычисляй его в одном месте и передавай как зависимость. Выбирай источник режима по контракту компонента, не полагайся на случайную truthy-проверку идентификатора.

## Поля и заголовок

В `DataFormAPI` держи определение полей, совпадение их id с моделью, labels, обязательность и зависимые настройки. Используй публичные возможности AForm. Не собирай параллельный механизм формы вручную без необходимости.

В `HeaderAPI`, когда он нужен, вычисляй заголовок и подписи по режиму. Возвращай ключи переводов по соглашениям проекта; не дублируй там вычисление режима или загрузку модели.

## Сохранение и ошибки

`SaveAPI` предоставляет `save`, `saving = ref(false)` и `errors = ref({})`.

В `SaveAPI` выполняй запросы через `AHttpAPI` из `aloha-vue`, используя существующую конфигурацию проекта. Перед запросом защищайся от повторного сохранения, очищай ошибки предыдущей попытки и устанавливай `saving`. Подготавливай payload из модели, выбирай create/update по режиму. Соблюдай HTTP-контракт проекта без фиксированных endpoints и предположений о сервере.

При успехе можно показать уведомление через `ANotificationAPI` из `aloha-vue`. Передай результат владельцу окна через существующий контракт callback или события, затем закрой окно. Не навязывай имя поля результата и не выполняй дополнительную загрузку без необходимости.

При ошибке оставляй окно открытым, сохраняй введённые данные и показывай ошибки полей и общую ошибку через `errors` в формате AForm. Для ошибок формы достаточно `errors`, не дублируй их уведомлениями. Не теряй ошибки сети и неизвестные ответы: также показывай их через общую ошибку формы. Используй существующий helper ошибок, если он есть; не предполагай конкретную структуру DRF.

Сбрасывай `saving` в `finally`. Если глобальная обработка ошибок влияет на завершение запроса, проверь её настройки. Сохраняй возможность повторной попытки.

## Подключение AModalForm

Связывай `model` через `v-model`, описание полей через `:data-form`, ошибки через `:errors`, обработчик через `:save`, закрытие через `:close`.

В текущем API состояние загрузки называется `loading`: подключай `:loading="saving"`, а не несуществующий prop `saving`. Проверяй поведение блокировки в установленной версии; при необходимости используй `disabled` или `disabled-save` и защиту внутри `save`.

Настрой возвращение фокуса через `selector-close-ids` или другой поддерживаемый механизм. Сохраняй доступный заголовок, labels полей и клавиатурное управление. Для вложенных окон используй возможности фреймворка, а не произвольные значения z-index.

## Подтверждения

Логику простого подтверждения размещай в `views/<Page>/Confirms/<Name><Action>ConfirmAPI.js`, например `UserDeleteConfirmAPI.js`. Открывай окно через `AConfirmAPI`; там же держи действие, его загрузку и обработку результата. Для HTTP-запросов используй `AHttpAPI`, для уведомлений об успехе и ошибке — `ANotificationAPI`. В отличие от формы, ошибки подтверждения показывай уведомлением, а не через объект ошибок полей. Не создавай отдельный модальный компонент для простого подтверждения.

## Проверка

Проверь create и update, подготовку модели, отмену без изменения исходных данных, повторное открытие, успешное сохранение, ошибку и повторную попытку. Проверь блокировку повторного запроса и возвращение фокуса.

Тестируй наблюдаемое поведение: payload, состояние сохранения, ошибки, результат и закрытие. Используй реальные контракты Aloha-Vue и существующую инфраструктуру тестов проекта. В результате укажи выполненные проверки и непроверенные сценарии.
